# Bench 2026-09-22 — the read path, verified, and a defect it exposed

Serial 23030927, plate `square96-19mm-eric-test` (model `square_96_19mm`,
19 mm square-well), wells A1-C3. Run as the `plate-reader-uv-smoke` readout
capability check. Everything here is measured.

## Result

| scan | points | wells | outcome |
|---|---|---|---|
| absorbance 350-800 nm @ 10 nm | 46 | 9 | complete, 414 values |
| emission 400-700 nm @ 10 nm, ex 360 nm | 31 | 9 | complete, 279 values |

693 measurements, no errors. `read.absorbance` and `read.fluorescence` are now
bench-verified on a real plate; `read.luminescence` still is not.

**The 19 mm geometry reads cleanly.** That was the open worry — a 19 mm plate
against a ~14 mm standard — and it is settled for both read paths: no `5B00`
focus refusal, no geometry error, replicates agreeing down each column
(A2/B2/C2 within 0.003 AU at every wavelength).

## What the plate did

Absorbance saturates at the UV end and clears by 440 nm:

| wells | over-range | reads |
|---|---|---|
| A2, A3, B2, C2 | none | 46/46 |
| B3, C3 | 350 nm only | 45/46 |
| A1, B1, C1 | 350-400 nm | 40/46 |

Column 1 peaks at 410 nm (A ~2.2-2.4); A3 reads 3.997 at 350 nm, essentially
at the ceiling. Emission has **no** saturation anywhere, peaking at 400-410 nm
— the blue edge of what 360 nm excitation can reach. The true maximum may lie
below 400 nm and is not reachable here: the em-ex gap is already near the
~20-30 nm floor below which the monochromator passes scattered excitation.

The scan was requested as 400-800 nm and run as 400-700. The **700 nm ceiling
is the hardware's**, not the driver's: the Cytation 5 spec sheet gives emission
as 300-700 nm (`docs/INDEX.md`). So the ten points above 700 nm are not
missing data — they are not measurable on this instrument by any route, Gen5
included. An earlier note in this session left that open; it is closed.

Per the design's criteria: **Confirmed** for A2/A3/B2/C2, **Inconclusive** for
the five wells with over-range points — usable above ~410 nm, needing dilution
only for the UV end.

## The defect this exposed

The 46 absorbance reads all succeeded. The **first** fluorescence read of the
same region, ex 360 / em 400, was refused:

```
503  Cytation refused 'O': status '2D06' — checksum landed in the
     rejected 94-99 band, which _pad_for_checksum is supposed to avoid
```

`_pad_for_checksum` had guarded this since 2026-08-23 — but was wired into
`read_absorbance` **only**. Fluorescence and luminescence went out unguarded,
and no fluorescence read had ever been taken on a real plate to find out.

The three command frames are genuinely different, which is why one shared
checksum could not have covered them:

| read | opcode | checksum |
|---|---|---|
| absorbance | `004701` | `sum % 100` |
| fluorescence | `008401` | `(sum + 7) % 100` |
| luminescence | `008401` | `(sum + 8) % 100`, integration time in the body |

Both offsets come from `biotek_backend`, whose own comments on them read
"don't know why +7" / "+8".

Scope, computed over this sweep: **13 of the 31 emission points** land in the
rejected band (400-440, 500-530, 600-620, 700). Not a rare unlucky wavelength —
nearly half the scan, and the sweep's first point is one of them.

Fixed in `1d7d2da`: the guard is generalised over a checksum function and wired
into all three reads. Deployed to the device PC and **verified on hardware the
same session** — the re-run's first point was em 400 nm, the exact read that had
been refused, and all 31 points then completed.

Cost of the guard: a padded fluorescence read takes ~35 s against ~20 s
unpadded, because the instrument reads every well in the grown rectangle. The
extra wells are discarded; the response carries only the wells requested.

## Two deployment traps, for whoever updates this PC next

Neither is about the instrument; both would break it.

1. **`Projects\update.ps1` is wrong for this repo.** It hardcodes
   `uv sync --extra api`, but `pylabrobot` lives in `plr`, `pylibftdi` in
   `windows`, and imaging in `imaging`. That sync prunes the whole driver
   stack. RUNBOOK.md already documents the resulting
   `RuntimeError: pylibftdi is not installed`. The correct command is
   `uv sync --extra api --extra plr --extra windows --extra d2xx --extra imaging`.

2. **`uv sync` tries to delete PySpin.** The FLIR camera SDK is installed
   manually and is not declared in `pyproject.toml`, so any sync treats it as
   stray. On 2026-09-22 the removal failed only because the running service held
   `GCBase_MD_VC140_v3_0.dll` open. With the service stopped, imaging would have
   gone. The `cytation` service runs `uv run --no-sync` — that flag is
   load-bearing, not incidental.
